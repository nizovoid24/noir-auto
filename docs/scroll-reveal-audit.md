# NOIR AUTO — диагностика анимаций появления при прокрутке

Дата: 11 ноября 2026 года.
Статус: анализ завершён; рекомендации не внедрены.

## 1. Задача и границы проверки

Проблема: секции и элементы визуально появляются слишком резко и быстро, а анимации воспринимаются как рваные при отсутствии явных ошибок.

Проверены исходники компонентов и CSS, места подключения SectionReveal и соответствующий код установленной Motion. Выполнен математический расчёт текущей cubic-bezier-кривой. Это статическая диагностика: инструментальный замер FPS, запись Performance trace и отдельная проверка на физическом мобильном устройстве не проводились. Нагрузочные риски ниже являются гипотезами, а не подтверждёнными причинами пропуска кадров.

Код, стили, зависимости и исходные изображения в рамках анализа и сохранения отчёта не изменялись. Добавлен только этот документ.

## 2. Основной вывод

Наиболее вероятная причина ощущения резкости — сочетание короткой активной фазы общей анимации и агрессивного easing. При duration 0.7 секунды кривая [0.16, 1, 0.3, 1] выполняет примерно 86% перехода за первые 0.2 секунды. Большая часть оставшегося времени почти не воспринимается визуально.

Дополнительные факторы: отсутствие stagger у карточек услуг, появление крупных композиций целиком и несогласованное покрытие конфигуратора анимациями. Прямой конфликт CSS transition и Motion на scroll-reveal обёртках не обнаружен.

### Фактический ритм текущей кривой

Расчёт выполнен математически для duration 0.7 s. Это прогресс заданного перехода при нормальном исполнении, а не измерение кадров браузера.

| Время после запуска | Прогресс | Остаток смещения из 24px |
|---|---|---|
| 100 ms | 62.8% | 8.93px |
| 150 ms | 77.6% | 5.38px |
| 200 ms | 86.4% | 3.26px |
| 300 ms | 95.1% | 1.17px |
| 350 ms | 97.2% | 0.68px |

Поэтому номинальные 700 ms ощущаются как значительно более короткое появление. Простое увеличение duration со старой кривой лишь частично исправит восприятие.

## 7. Layout, paint и потенциальная нагрузка

### Подтверждено по коду

- Scroll reveal анимирует только opacity и transform. Нет анимации width, height, margin, padding, top или left у SectionReveal.
- Нет layout/layoutId-анимаций Motion, бесконечных циклов, анимируемого blur/backdrop-filter и собственного покадрового React scroll-обработчика.
- Изображения имеют размеры и/или aspect-ratio: место под них предусмотрено. Явной причины скачков из-за незарезервированной высоты фотографий не видно.
- Hero использует крупное масштабируемое изображение с mask-image и статическими градиентами. Значения градиентов и маски не анимируются.
- BeforeAfterSlider обновляет CSS-переменную, clip-path и left абсолютных линии/маркера при взаимодействии. Изменение left может затрагивать локальное позиционирование, но не относится к scroll reveal.
- Список расшифровки конфигуратора монтируется и меняет высоту панели без layout-анимации. Это отдельный источник резкого изменения интерфейса при выборе услуг.

### Риски, требующие измерения

- PNG услуг весят примерно 1.7–2.8 МБ каждый. Lazy loading и decoding=async не исключают затрат на первое декодирование и подготовку изображения к отрисовке.
- Несколько фотографий могут впервые отображаться одновременно с синхронным reveal карточек.
- Philosophy, Before/After и Final CTA перемещаются крупными контейнерами с изображениями; площадь содержимого больше, чем при раздельном появлении небольших элементов.
- Маски, крупные текстуры и прозрачные слои Hero могут повышать стоимость композитинга на слабых устройствах, особенно если пользователь начинает прокрутку до окончания вступительной анимации.

Ни один из этих рисков нельзя объявлять подтверждённым падением FPS без Performance trace на целевом устройстве.

## 8. Рекомендации — не внедрены

### Первый приоритет: темп и easing

| Параметр | Сейчас | Отправная точка для настройки |
|---|---|---|
| Duration общего reveal | 0.7 s | 1.1 s |
| Easing движения | [0.16, 1, 0.3, 1] | [0.22, 0.61, 0.36, 1] |
| Начальная translateY | 24px везде | 24px desktop, 16px mobile |
| Opacity | Общая кривая с движением | Отдельный fade 0.9–1.0 s с [0.25, 0.1, 0.25, 1] |
| Delay одиночного блока | 0 | 0–0.08 s |
| Stagger SERVICES | Нет | 0.10–0.12 s между карточками видимого ряда |
| Stagger PROCESS | Нет | 0.10–0.14 s между этапами на desktop |
| Once | true | Сохранить true |

Не увеличивать только duration: прежний easing сохранит быстрый старт даже при более длинном переходе.

### Второй приоритет: условия запуска и композиция

1. Разделить настройки небольших и высоких блоков. Для заголовков/карточек проверить amount 0.15–0.2; для высоких фотографических блоков — 0.05–0.1. При необходимости проверить отрицательный нижний viewport.margin около -40px. Не назначать повышенный порог сразу всем элементам.
2. На мобильных сохранить независимый запуск карточек по мере входа в экран. Не выстраивать все шесть карточек в длинную очередь задержек.
3. Фото и текст Philosophy/Final CTA можно проявлять раздельно с небольшим интервалом 0.10–0.15 s, без дополнительного scale.
4. Согласовать reveal конфигуратора: добавить спокойное первое появление области выбора и панели расчёта, не перезапуская его при каждом изменении выбора.
5. Hero оставить без изменений на первом проходе. Он не использует общий scroll reveal и требует отдельной оценки.
6. Не добавлять длительную задержку на уже видимые интерактивные элементы и не скрывать доступный контент ради эффектов.

### Третий приоритет: измерение производительности

- Записать Performance trace при первой прокрутке и при повторном просмотре: сравнить декодирование изображений, paint/composite, длинные задачи и пропуски кадров.
- Отдельно проверить production-сборку и мобильное устройство, а не только dev-режим.
- Если реальная нагрузка подтвердится, создать отдельные WebP/AVIF и адаптивные варианты изображений, сохранив оригинальные PNG.
- Не назначать will-change всем обёрткам постоянно. Использовать только локально и при подтверждённой пользе.
- Сохранить reduced motion: без пространственного движения, stagger-задержек и принудительного ожидания.

## 9. Критерии будущей проверки после изменений

- Появление заметно распределено по времени, без доминирующего рывка в первые 100–200 ms.
- Карточки SERVICES и этапы PROCESS имеют согласованный ритм на desktop.
- На мобильных нет длинного ожидания уже видимого контента.
- При возврате вверх reveal не запускается заново.
- Конфигуратор и Before/After остаются доступны во время взаимодействия.
- В reduced motion элементы сразу доступны без смещения и задержек.
- Если заявляется устранение падения FPS, результат подтверждён измерениями до/после.
